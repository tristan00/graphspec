**Model search**

| Where | What is there |
|---|---|
| `statement.py` | The record of every choice of a fit and a search, and the parser of what a split may see |
| `families/` | Kinds of model: what each reads and offers (`model_spec.py`), how each is built (`models.py`), the registry of heads by kind of target, `HEADS` (`heads.py`), the layers they share (`layers.py`, `periods.py`), and one module per family: `snapshot.py`, `mixed.py`, `event_graph.py`, `memory.py`, `projection.py`, `sequence.py`, `tree.py`, `walks.py`, `affinity.py`, `signal.py` |
| `bank/` | Building a bank (`build.py`), opening it (`bank.py`), deriving and caching its variants (`variants.py`) |
| `batches/` | Windows, inputs, gathers and packing of batches to the device |
| `measures/` | The registry of measures, `MEASURES` (`measures.py`), and the score by which a search ranks trials (`objective.py`) |
| `fits/` | One training (`training.py`), the registry of losses, `LOSSES` (`losses.py`), its budget of time (`budget.py`), the check of models (`check.py`) |
| `searches/` | The runner (`run.py`), selectors (`selector.py`), candidates (`space.py`), surrogates (`surrogates.py`, `tpe.py`), records (`records.py`) and reports (`report.py`) of a search |
| `api.py`, `dashboard.py`, `web/`, `__main__.py` | Public calls, the dashboard, the command |

A module imports only its own group, the groups below it and any of `graphspec`; `tests/test_standing.py` holds the order.

`tuning` turns staged graph tables or a graph database into a frozen bank of truth graphs, then searches graph-transform specs and temporal graph models over it on a CUDA GPU. Models and the search read structure from the bank's pinned declaration. No code here names a node type, relation or attribute. The database contract and task file are in the [root README](../README.md), and the transforms in [graphspec/README.md](../graphspec/README.md).

Commands require an absolute `GRAPHSPEC_HOME` before Python starts. Use the checkout launcher with mandatory `-Home`, for example `./scripts/graphspec.ps1 -Home D:/graphspec-runtime search run --bank D:/graphspec-runtime/banks/demo --output D:/graphspec-runtime/runs/demo-tuning --device cuda --seed 1 --derivation-seed 1 --seconds 600 --preparation-seconds 300 --workers 4 --variant-gb 64 --batch-sequences 64 --continuous --selector botorch --startup-trials 10 --mix random=25 tpe=25 forest=25 botorch=25 --random-params model/view`. Outputs stay outside code directories and, on Windows, on the configured runtime volume. Caches and temporary files live under that home. No profile settings or default home are consulted; see [storage](../docs/loader.md). For long jobs, `./scripts/detached.ps1 -Home D:/graphspec-runtime -Log D:/graphspec-runtime/logs/NAME.log` followed by the same arguments starts the command through WMI, so it belongs to no terminal or agent and survives the launcher; it prints the pid, and the log receives stdout and stderr.

**Bank**

`python -m tuning.bank.build` reads its explicit source once and writes each graph's truth arrays under `truth/`, with the options the generators of options its schema states drew for its decisions (see the contract, Generators of options). Training never touches the database. Labels live in `supervision.json`, apart from the model inputs. `Bank` refuses a manifest from another bank version or whose declaration does not reproduce its fingerprint.

`Bank.viewed(cfg)` shows the graphs of a bank under the choice of steps of the configuration and keeps the views under `cache/banks/<bank-digest>/views/<digest>/graph_NNNN/`; a graph whose tasks name observers is shown once per observer, so the graphs a fit reads are those of the view and are numbered by it. `Deriver.arrays` materialises graph variants under `cache/banks/<bank-digest>/variants/<digest>/graph_NNNN/`. The digest is of the key the contract states under The key of a variant: the schema, the source, the pipeline with the version of each operation, the settings except those used only during packing, the representation groups, what the splits may see, the device of dense algebra as the statement names it, the seed, the versions of the code of views, derivation and representations, and the name and version of every registered entry the variant reads; `<bank-digest>` holds the digest of what the build stored, `stored_sha256` of the manifest, never a time, and the version of views, and the digest of a folder of views the name and version of every registered entry the views read. No file is hashed: a standing test fails when the code of an operation, of a shipped entry of a registry, or of views, derivation or representations, changes and its version does not, and an entry registered from outside states its version, which whoever changes its code raises, so a variant made by other code is never read; a bank is opened to read with `Bank(directory)` and to derive with `Deriver(directory, device, seed, resident)`, `seed` being the `derivation_seed` of the statement. The runner prepares variants with `--workers` and, between trials, prunes the variant cache of every bank under the runtime home together to `--variant-gb`, least recently used first; the current trial's variant is kept. One budget covers all banks, so older searches' variants give way to the active one. Preparation counts against the trial deadline.

Every variant is built by the one engine of the graphspec README, a separate graph as one segment. `graphs/join=single` joins groups of `graphs/join_size` truth graphs, formed in the order of their names among the graphs whose rows fall in the same splits (`bank.grouped`), each onto one step axis, and builds each group graph by graph, so memory stays near one graph whatever the group size. Groups build in parallel across `--workers`; when a split has fewer groups than workers, the workers are spread over its graphs. Windows of a joined group use a window-local entity index: the entities the window references, renumbered, instead of every entity of the group, and the batch budget counts each window's distinct observed entities. A batch draws its windows from groups covering about 64 graphs, as separate graphs do. Joined arrays up to 4 GiB are held on the training device, and resident joined graphs are evicted least recently used beyond 12 GiB. Large joined arrays use temporary memory-mapped files and bounded copies on the runtime volume. The history of periods uses sorted indexes of observations and of the first nodes of tasks. The array store retains 128 graph stores; the resident cache retains 192 graphs. Arrays over 64 MiB remain mapped, and packing transfers only requested feature rows to the training device. Observation features are stored once: a variant holds `x_ref`, one row number per observation, and the feature table `x_table`, the `obs_x` of the views of its graphs. A batch selects rows from each graph's resident arrays and concatenates only what it selected.

**Packing**

`bank/bank.py` owns bank storage and variant identity, `batches/inputs.py` builds model inputs from graph windows, and `batches/tensors.py` resolves deferred gathers onto the training device. `batches/batching.py` combines independent windows and `batches/packing.py` owns worker processes and their transfer buffers.

`recipe` prepares one window as NumPy arrays and deferred feature gathers. Numba kernels implement graph traversal and sampling; sorted indexes bound row searches. `recipe_batch` combines equal-length independent windows, and `materialise` resolves their gathers together while preserving row order and duplicates. Views whose rows do not interact (tree, walks, sequence, mixed, event graph) narrow a window's rows to the span of its supervised rows; memory and projection compute neighbour histories for supervised rows only. For the snapshot view, except with coupling edges, a batch builds each graph's overlapping frames once: the input and spatial layers run on those frames and the result is expanded to the windows, and per-window edges are built only for the graph-cell and evolving modes, which read them per frame.

`packing.Packer` prepares batches in worker processes using two shared-memory slots per worker. Worker processes start with their numeric libraries limited to the worker's thread share, which keeps an idle worker near 1 GB. CUDA receives each packed batch from a registered slot. A prefetch thread loads upcoming resident arrays within the graph-cache window; large mapped tables gather rows on demand. Small feature tables remain on the training device.

**Models**

A model is built from a model spec: a tree of parameters whose root, `view`, names the packed input the network reads, and whose other parameters switch the components that exist for that view. Every component below is read by some parameter, and every parameter is read by some component; a parameter is present in a spec only while the switch that needs it is on. `python -m tuning.fits.check` runs one configuration per switch setting and records any parameter of the built network that receives no gradient; the test suite fails on one. It probes the last window of its graph that holds a point the loss reads (`tuning.fits.losses.counting`, the rule by which training skips a batch), passing over later windows as training passes over such a batch, and records how many it passed over under `skipped`; probing a window whose loss reads nothing would report every parameter as receiving no gradient, which is the defect the check looks for, so a graph with no such window stops the check naming it. Each view reads the base arrays plus the representation groups listed; only those groups' parameters enter its graph spec space. Every view reads the references of a task as a set keyed by name, as [the contract](../docs/contract.md) states under What a family reads: it embeds every member node with its own machinery below, pools the members of each reference by their mean with the place of a member of an ordered reference added, projects each reference by a matrix of its own name and sums them, and reads a reference to the graph as the pooled state of the graph. Each network ends in a head over that readout and the projected features of the task, which hold the attributes of its graph, plus a learned embedding of the kind of the task: a projection of the task shared by every kind of target, and one head per kind of target the bank holds, which gives each point of its kind one prediction from the projection of its task and a learned embedding of its series. Heads are registered in `tuning.HEADS` under the name of their kind of target as `tuning.families.heads.Attached(reads, module)`: `reads`, the parameters of the model it reads, and `module(hidden, spec, registry)`, which builds a module whose `forward(h, series, b, points)` gives the predictions of the points of the batch `points` names, `h` and `series` being theirs, and reads the inputs of their kind of target as `b["field/<name>"][points]`; the batch holds no target and no outcome of a kind of target (`inputs` and `outcomes` in the contract). The head of a number reads the task and the series, and so does the head of a decision, which is the head of a number, since no model reads an option; the head of a path also an encoding of the point's `tau`, by `time/encoding`, which a model therefore states wherever the bank holds paths; the head of a time to an event is the head of a path, its value per interval read as the logarithm of the odds of the event in the interval, given that it has not happened before; the head of a kind over classes gives each class of a task a score, the product of a projection of the task with the embedding of the class plus a bias read from that embedding, so that scores of one task differ by class and by task. The head of a sequence scores each point, a token at a place, the same way from the task and a learned embedding of the place added to it, with a bias read from the token and the place, up to the greatest length its kinds of task state; every place is predicted at once from the task, never from the tokens before it, which a target holds and a model never reads. A kind of target whose points name nodes (`names` in the contract) gives its head beside the task a projection of the node of each point, which every family embeds with its own machinery for a member of a reference, as a member under a name of its own that no reference pools and only the head reads; walks from such a node are drawn when the batch is packed, by the function the representation uses, keyed by the hash of the node's kind and key, the time and the graph of the step. The head of such a kind scores each point as the product of a projection of its task and series with the projection of its node, plus a bias read from the node. A batch holds per point its task among the rows of the batch (`point_row`), its series, its kind of target (`aim`, its place among the kinds of target of the bank), its weight and the inputs of its kind of target; every bank is laid out by points, a number being one point of its task. Every view that reads edges reads the relation of an edge, stated or taken from a column, through a learned embedding of its code added to what the edge carries: the message of a `relational` spatial layer, the node of a relation event, the event features of a memory, a sampled interaction partner, a node of the tree and a hop of a walk. Weights held per relation are held per table, so a table whose relations are taken from a column holds one set whatever the number of its values. `mixed`, `affinity` and `signal` read no edge. Entity numbers are graph-local correspondence keys; no network learns an embedding per entity id.

`hidden` sets every learned width except the affinity state, whose width is the number of kinds of task seen as events. `dropout` is present only where a component applies it: snapshot spatial layers, causal attention in the snapshot and sequence views, temporal-edge message layers in the snapshot and event-graph views, and mixed message layers. Event and token time gaps enter the memory, projection, sequence, tree, walk, event-graph and coupling components through `cos(w · log1p(gap) + b)` with learnable `w` and `b`; period gaps enter through linear maps of `log1p(gap)`; the mixed view carries its edge gap as a linear feature; the affinity and signal views read no gaps.

The components descend from published designs and depart from them; the names above say what runs, not which paper. For the record: the graph cell follows GConvGRU and, with diffusion hops, the DCRNN cell; the evolving convolution follows EvolveGCN-H; the mailbox update follows TGN with a mean aggregator and no edge features in attention keys; the mutual RNN follows JODIE without its trajectory loss; the intensity update follows DyRep with attention over the current frame in place of its neighbourhood matrix and without the survival loss; the antisymmetric integrator follows CTAN with a mean neighbourhood term; the projections follow TPNet; the pair terms follow TNCN; the mixer follows GraphMixer with a learnable time encoding and no link features; the transformer with `occurrence` follows DyGFormer and with `overlap` HyperEvent; the selective state-space operator follows DyGMamba without patching; the tree follows TGAT with one head; the walks follow CAWN; the affinity state follows NAViS with a regression head; the signal network follows MTGNN with one gated convolution per layer. Every path trains the heads of the kinds of target of its bank with the losses its statement names; none of the papers' own ranking or point-process losses is implemented.

**Training protocol**

- The statement of a fit and of a search is one versioned record, `tuning/statement.py`, at version 4. It holds `version`, `device`, `seed`, `derivation_seed`, `seconds`, `preparation_seconds`, `workers`, `variant_cache_bytes`, `batch_sequences`, `trained`, `scored`, `sees`, `loss` and `measures`. `trained` and `scored` name the splits trained on and scored on, which share no split, and `sees` states for each of them the registered rules of what its tasks may see; the splits trained on are those the bank was built for. `loss` maps every kind of target of the bank to the registered loss of its points, such as `{"number": "squared", "class": "entropy"}`, and the fit trains with their sum; a kind of the bank it does not name, a kind the bank does not hold, or a loss that does not read its kind stops the fit, and a search when it starts, naming them. `measures` names the registered measures the fit records, at least one; each is computed over the points of the kinds of target of the bank it reads, and a measure that reads none of them, or a kind of the bank that none reads, stops the fit and the search naming it. Neither has a default. The device is `cpu`, `cuda` or `cuda:N` with N a GPU that is present; the seed is an integer from 0 to 2^32 - 1; `derivation_seed`, the seed of every draw of the derivation of a variant (sampling, dropping, rewiring, negatives, walks and the neighbours packing samples), which the key of every variant holds, is an integer from 0 to 2^64 - 1, and the library holds no seed of its own; `workers` is between 1 and the number of logical processors; seconds, bytes and batch sequences are positive integers. The record is built only through its checks. Every field is required; an absent field, an unknown field or a value outside its meaning stops the run with an error naming the field. A search builds it from `--device`, `--seed`, `--derivation-seed`, `--seconds`, `--preparation-seconds`, `--workers`, `--variant-gb` and `--batch-sequences`, and writes the statement of each trial to `statement.json` in the trial's directory; it is the statement of the search with the seed of the trial, which is drawn from the seed of the search and the trial's index, and with the derivation seed of the search, which every trial shares so that trials stating one variant read one cache. `config.json` holds copies of that seed and of the seconds as `seed` and `max_seconds`; a copy that is absent or differs stops the run with an error naming it. A fit stores its statement in `result.json`.
- A fit runs on the device of its statement. `cuda` with no GPU present stops with an error naming the device. Dense algebra of derivation moves to that device for a component of 1,024 nodes or more when the device is a GPU.
- The optimizer is AdamW, fused on CUDA.
- Every fit sees every row of the splits trained on exactly once per epoch, for every requested epoch, and scores every row of the splits scored on. Each epoch checks the exact row ids for omissions, duplicates and rows of other splits. A task that carries a weight enters the loss with it.
- A training window ends at a labelled step s and covers steps s−H+1 to s, with H = `time/history`. It supervises only the targets at s. Where a step may hold several tasks, a window holds at most 1,024 of them, so a step with more gets several windows over the same steps.
- With `time/context` c above 0, a window that starts in period p starts instead at the first step of period max(0, p−c). Each family gets its period-end readout. Replayed steps add no supervised rows.
- A batch groups windows of equal length, `batch sequences × 16 // H` of them. It holds at most 1,024 frames, 1,024 prediction rows, 1,048,576 entity-frames and 4,194,304 facts, where a window contributes its steps times its graph's entity count and times its graph's facts per step from the manifest.
- On a GPU the infra layer reserves the GPU memory a fit or model check may use.
- Batches hold windows of one length. They are formed within chunks of 64 graphs: each epoch shuffles the graphs, cuts them into chunks, forms every batch inside its chunk and shuffles the batches of a chunk, so the feature matrices an epoch touches are loaded about once each rather than once per batch. `batching.batches` has no default shuffle: training states `Shuffle(seed, epoch, identities(bank, cfg))` with the seed of the statement, and scoring states `None`, which keeps the order of its windows. The shuffle is keyed, never drawn from a generator: graphs are ordered by `hashing.unit(seed, "tuning.batches/graphs", identity, epoch)`, where the identity of a graph is the hash of the name of its view, or of the names of the views of a joined group in their order, then by the identity where draws tie; a graph's windows keep their order; the batches of a chunk are ordered by `hashing.unit(seed, "tuning.batches/groups", ...)` of the identity and the window of their first block and the epoch. The batches of an epoch therefore do not depend on the order of the graphs in the bank or the numbering of their entities.
- Sequence and memory states reset at window boundaries. Event models start from the last features known before the window.
- Targets of a kind of target that scales are standardised per series with the mean and sample standard deviation of the rows of the splits trained on; those of a kind that does not are read as stated. Predictions are converted back before the measures are computed.
- Losses are registered in `tuning.LOSSES` and measures in `tuning.MEASURES`, apart from the kinds of target; each states `reads`, the kinds of target it reads, and a name registered twice stops with an error. A loss is called with the predictions of the points of its kind of target in a batch, those points of the batch, `weight`, `series`, `aim`, `point_row` and the inputs of the kind, joined by `target`, in the type of the predictions, and the outcomes of the kind, which `tuning.fits.losses.outcomes` reads from the bank by the rows of the batch since no batch a model reads holds them, and which replace the inputs of the batch, each in the type the bank holds it (see `outcomes` of Kinds of target in the contract), a negative taking those of the point of its link, with `tasks`, the number of rows of the batch, and with the bank, and gives a number to minimise; a batch without points of a kind adds nothing for it. A measure states `better`, `higher` or `lower`, a `label` and a `short` label, and `refusal(held)`, which reads the targets, tasks, series and fields of the points `held` and never their predictions, and gives nothing where the measure can be computed over them and otherwise the reason it cannot; `tuning.measures.measures.needless` states a measure without needs. Before a measure is computed, and when a fit or a search starts over the targets the bank holds for the splits scored on, every series it reads must have a point and its `refusal` must give nothing, or the fit or the search stops naming the splits, the series or the measure (`tuning.measures.measures.measurable`); a fit therefore never trains to be refused by a measure, except where its pipeline leaves out every task of a link of a series. A measure is called with the points scored of the kinds of target it reads, `target` and `prediction` in the units stated, `task`, `series`, the names of their series, their scale and `fields`, the inputs and outcomes of every kind of target of the bank per point in the types the bank holds them, so that times are compared as whole numbers, and gives `value` and, under `series`, a value per series. A fit records `loss` and, under `measures`, the record of every measure it states, and under `unmeasured` the number of tasks of each kind whose target is a link that the measures leave out for having fewer candidates than their stated count of negatives plus one, those left out because the pipeline did not keep the node they start from or link to among them; `predictions.npz` holds the rows, predictions, targets and series of the points scored, and the inputs and outcomes of their kind of target, and under `drawn_row` and `drawn_prediction` the negatives scored beside the point of each link (see Links among sampled negatives in the contract). A batch holds the points of each of its windows in turn, the candidates of every task of a link, its node and its negatives, in the order of the tokens of their nodes, so that no place in the batch tells the node a task links to from its negatives; `rows` holds the rows of the points of the bank, `drawn` the row of the link of each negative, and `placed` the place of every point of the batch among `rows` followed by `drawn`, through which the loss reads targets and a fit stores predictions; `left` marks, per row of `rows`, the point of a task whose target is a link and whose start or named node the variant does not hold at its step (`row_left`): it has no node and no negative, the loss reads none of its points, and a batch whose every row is left makes no update; every row of a split is checked against `rows` alone. The losses, the measures, the check of the measures when a fit or a search starts and the scaling of the series read only the points `counted` of the bank: every point but those of a decision whose option was not chosen, which are stored, packed and predicted and enter no loss and no measure, so that a fit reads of a decision its task and the outcomes of its options chosen (see Decisions in the contract); a batch with no point counted makes no update, and `result.json` counts such batches under `skipped`. A fit or a search on a bank whose schema gives options by a rule stops when it starts, naming the kind of task and the rule, unless the kind of task states a generator of options that reads its rule, whose options the build drew. Predictions are the predicted targets the kind of target gives from the values of the model (`predicted` in the contract), such as the probability of each class, and measures read those.

- The saved checkpoint is reloaded and must reproduce the first validation batch.
- The configured `--seconds` budget covers selection, layout, source capture, variant building, packing, training, and evaluation. At the deadline the runner records a timeout and waits for every owned worker to exit before continuing. Pruning runs after cleanup, outside the trial budget. Late outputs are retained with `late_` names; incomplete trials receive no prediction score. `trial.json` records phase timings.

**Search**

| Selector | How trials are chosen |
|---|---|
| `--selector forest` | SMAC-style selection: a random forest fitted to the log of completed scores predicts each candidate's MSE, the spread across its trees stands in for uncertainty, and a second forest fitted to all completed, failed and timed-out trials predicts completion. Log expected improvement over the best observed MSE, computed in log space, plus three times the log completion probability ranks 10000 uniformly drawn valid configurations. Parameters selected by `--random-params` are drawn first and held fixed. |
| `--selector botorch` | BoTorch fits a MAP-SAAS Gaussian process to completed scores and a separate feasibility model to all completed, failed and timed-out trials. Both models fit on the device of the statement, and log expected improvement ranks 10000 uniformly drawn valid configurations to pick one. Parameters selected by `--random-params` are drawn first and held fixed in every candidate evaluated by the model. |
| `--loss`, `--measures` | The losses and the measures of the statement, the losses as `kind=loss` pairs, one for every kind of target of the bank; both are required and kept in `plan.json`, and a continued run states the same. Trials are ranked by the first measure, which states that lower is better; a search whose first measure states otherwise stops when it starts. The first measure reads only the points of its kinds of target, so a bank of several kinds is ranked by those kinds alone until ways of combining measures are stated (8.3). |
| `--objective` | `series=weight` pairs over the series the first measure reads, that blend its values per series into the one score trials are ranked by, for example `--objective level=1 trend=2`; without them trials are ranked by its value. A continued run keeps the saved weights unless new ones are given, and since every result stores each series' value, reweighting re-ranks finished trials without refitting. A plan written before measures were registered names no measures, and ranks its trials by the raw validation MSE or by its weights over the validation losses of its series, as it was written. |
| `--mix` | Percent of trials after the startup phase handed to each selector, as `name=share` pairs summing to 100, for example `--mix random=80 forest=10 tpe=10`; a new run states it; a continued run keeps the saved mix unless a new one is given. |
| `--selector tpe` | Optuna's multivariate, grouped TPE with 10 random startup trials, 64 expected-improvement candidates, and a good set of the best 100 trials. Model parameters are named `model/<parameter>`, training parameters by their names, settings `graph/<parameter>`, the presence of the entry N of the pipeline `pipeline/N` and its parameters `pipeline/N/<parameter>`. A model parameter enters a trial only while its condition holds; a setting only when the model's view reads its group and its condition holds; the parameter of an entry only while the entry is present and its condition holds. |
| `--selector random` | Each active model parameter, each training parameter and each active spec parameter drawn uniformly, in that order. |
| `--startup-trials N` | Minimum number of finished trials before the mix takes over; a new run states it. Completed, failed and timed-out trials count regardless of their original selector. Below this threshold new trials are random. Existing history is retained. `--random-trials` is an alias; plans retain the `random_trials` field. Legacy TPE uses this number as its initial trial-index threshold. |
| `--random-params model/view ...` | Fully qualified parameter names or wildcard patterns to keep random after BoTorch starts. Model names use `model/`, settings `graph/`, entries of the pipeline `pipeline/`, and training names are unprefixed. Draws obey the proposal bounds and remain fixed whenever active. Omission preserves a continued run's setting; supplying the flag without names clears it. |

For every proposal the runner rebuilds the optimizer from the trial files; there is no external study database. A completed result must match the frozen supervision fingerprint, cover every training row, score the complete validation split and have a finite score. Otherwise loading the result fails. BoTorch learns from the original recorded configurations, including history outside the current proposal bounds. Bounds constrain new proposals, not historical training inputs. Categorical values use one-hot encoding; numeric inputs use their declared ranges and logarithmic scales, with activity indicators for conditional values. Failed trials train feasibility without invented prediction scores. TPE retains its existing failure ranking and bound filtering, and leaves out a recorded trial whose pipeline and settings the statement refuses: only `graphspec.operations.operation.Refused`, which the checks of a statement alone raise, leaves one out, and any other error raised while checking it stops the selection. Interrupted trials are excluded from both learning and BoTorch's startup count.

`selection.json` records:

- the selector, seeds, settings, proposed parameters and failure history; BoTorch also records preset random values and every trial used for learning
- the model digest, its description, the model parameters that differ from their defaults and the model space
- the digest of the settings, the settings that differ from their defaults, and the model's space of settings; the digest of the pipeline, its flags and parameters that differ from their defaults, and the space of the template
- prior trial ids with result hashes
- `bank_stored_sha256`, the digest of what the build of the bank stored, the supervision hash and the declaration fingerprint

Configuration and selection are saved before the worker starts, and a continued trial reuses them. `--bounds` narrows the space new proposals draw from; the bounds are stored in `plan.json` and in every `selection.json`. A bound on a choice or a flag that leaves out its default leaves the narrowed parameter without one, so that nothing reads a value the bound excluded.

The time limit of every trial is the `seconds` of the statement, and `--seconds` is required. `plan.json` holds copies of the statement's seed, derivation seed, seconds, workers, variant bytes, batch sequences, splits trained on, splits scored on, what each split may see, loss and measures; on continuation each copy must equal the statement given, and a copy that differs or a field that the plan lacks stops the run with an error naming it. `plan.json` holds as `bank_stored_sha256` the digest of what the build of its bank stored, `stored_sha256` of the bank's manifest: a continued run reads a bank that stored the same, so a bank rebuilt identically continues it, and a bank whose build stored anything else stops the run naming both digests. A new run states `--selector`, `--startup-trials`, `--mix` and `--random-params`; a continued run keeps the saved ones unless new ones are given. The dashboard and result exports expose older trials' recorded budgets under the same parameter without rewriting their original configurations.

To draw epochs randomly before BoTorch chooses the remaining parameters, use `--random-params model/view epochs` with bounds `{"epochs":{"low":1,"high":5}}`. The range includes every integer between its endpoints. Bounds that hold `max_seconds` are refused with an error naming it. BoTorch learns from historical runtime limits recorded with completed and failed trials. Missing historical limits remain unknown; the current plan's limit is never substituted for them.

A trial's configuration holds the model spec under `model`, the pipeline under `pipeline`, the settings under `graph`, the splits of the statement under `splits`, the training parameters below at the top level and `seed`. A search takes its pipeline as a template, `--pipeline FILE`, a JSON list of the operations in order with their labels and, for an operation that takes two graphs, the name of its second graph; a new run states it, `plan.json` keeps it, and a continued run states no other. The search draws which entries of the template are present and their parameters, never their order. Model parameters draw from these ranges; a parameter is drawn only while its condition holds. The parameters of the operations, the settings and their ranges are in [graphspec/README.md](../graphspec/README.md).

**Run directory**

The runner owns one trial at a time. Windows Job Objects and Linux process groups contain its descendants; uncertain cleanup stops the runner. `tuning.searches.records` validates trial identity, complete epoch and row coverage, finite scores, and outcome files. Completed, failed, timed-out, and interrupted attempts stay distinct; a worker that exited without an outcome is interrupted. Older plan versions require explicit migration.

`--trials N` ends a continuous run once N trials are recorded; a continued run takes the limit it is given. A file named `STOP` in the run directory stops the run after the current fit, and stops a continued run before its first trial. The runner refuses to continue while the worker named in `running.json` is still alive.

**Verification**

`python -m tuning.fits.check BANK --output checks.json --device cpu|cuda --seed N --derivation-seed N --trained ... --scored ... --sees ... --loss KIND=LOSS ... --pipeline pipeline.json --settings settings.json [--graph N]` runs forward, backward through the sum of the stated losses and checkpoint reload for one model spec per setting of every structural switch the bank offers, and records any parameter that received no gradient. Each derives its variant by the stated pipeline, with the settings its groups read taken from `settings.json`, which states every setting any of them reads; a setting it lacks stops naming it, and a key that no view's settings declare is refused. It runs on the last window of graph `N`, or of the graph with the most observations. A model that runs out of GPU memory is recorded and the check continues; the command then exits with the list of those models. Any other error stops it.

Two switches apply across views. `time/encoding` picks the time-gap encoding every temporal component uses: `log_cosine` is `cos(log1p(gap) w + b)` with learnable `w`, `cosine` the same on the raw gap, `log_linear` a linear map of `log1p(gap)`. `keys/embedding` adds a learned vector per entity key, hashed into a table of `keys/table` rows, to every entity encoder of the view: observation nodes, derived nodes, event endpoints, memory states, tree, history and walk nodes, and the member nodes of the references of a task. Only node types whose keys recur across graphs receive it: a bank marks a type shared when at least half of its distinct keys appear in two or more graphs, and other types get a zero vector, so identifiers that are unique to one graph never carry an embedding that could memorise the graph they came from. The table is a parameter trained by the training rows only, so holdout graphs see vectors learned from training graphs that contain the same key.

| Where | What is there |
|---|---|

| `families/` | Kinds of model: what each reads and offers (`model_spec.py`), how each is built (`models.py`), the layers they share (`layers.py`, `periods.py`), and one module per family: `snapshot.py`, `mixed.py`, `event_graph.py`, `memory.py`, `projection.py`, `sequence.py`, `tree.py`, `walks.py`, `affinity.py`, `signal.py` |
| `bank/` | Building a bank (`build.py`), opening it (`bank.py`), deriving and caching its variants (`variants.py`) |

| `measures/` | The score by which a search ranks trials (`objective.py`) |
| `fits/` | One training (`training.py`), its budget of time (`budget.py`), the check of models (`check.py`) |
| `searches/` | The runner (`run.py`), selectors (`selector.py`), candidates (`space.py`), surrogates (`surrogates.py`, `tpe.py`), records (`records.py`) and reports (`report.py`) of a search |
| `api.py`, `dashboard.py`, `web/`, `__main__.py` | Public calls, the dashboard, the command |

A module imports only its own group, the groups below it and any of `graphspec`; `tests/test_standing.py` holds the order.

`tuning` turns staged graph tables or a graph database into a frozen bank of truth graphs, then searches graph-transform specs and temporal graph models over it on a CUDA GPU. Models and the search read structure from the bank's pinned declaration. No code here names a node type, relation or attribute. The database contract and task file are in the [root README](../README.md), and the transforms in [graphspec/README.md](../graphspec/README.md).

Commands require an absolute `GRAPHSPEC_HOME` before Python starts. Use the checkout launcher with mandatory `-Home`, for example `./scripts/graphspec.ps1 -Home D:/graphspec-runtime search run --bank D:/graphspec-runtime/banks/demo --output D:/graphspec-runtime/runs/demo-tuning --device cuda --seed 1 --seconds 600 --preparation-seconds 300 --workers 4 --variant-gb 64 --batch-sequences 64 --continuous --selector botorch --startup-trials 10 --mix random=25 tpe=25 forest=25 botorch=25 --random-params model/view`. Outputs stay outside code directories and, on Windows, on the configured runtime volume. Caches and temporary files live under that home. No profile settings or default home are consulted; see [storage](../docs/loader.md). For long jobs, `./scripts/detached.ps1 -Home D:/graphspec-runtime -Log D:/graphspec-runtime/logs/NAME.log` followed by the same arguments starts the command through WMI, so it belongs to no terminal or agent and survives the launcher; it prints the pid, and the log receives stdout and stderr.

**Bank**

`python -m tuning.bank.build` reads its explicit source once and writes each graph's truth arrays under `truth/`. Training never touches the database. Labels live in `supervision.json`, apart from the model inputs. `Bank` refuses a manifest from another bank version or whose declaration does not reproduce its fingerprint.

`Bank.viewed(cfg)` shows the graphs of a bank under the choice of steps of the configuration and keeps the views under `cache/banks/<bank-digest>/views/<digest>/graph_NNNN/`; a graph whose tasks name observers is shown once per observer, so the graphs a fit reads are those of the view and are numbered by it. `Bank.arrays` materialises graph variants under `cache/banks/<bank-digest>/variants/<digest>/graph_NNNN/`. The digest is of the key the contract states under The key of a variant: the schema, the source, the pipeline with the version of each operation, the settings except those used only during packing, the representation groups, what the splits may see, the device of dense algebra as the statement names it, the seed and the versions of the code of views, derivation and representations; `<bank-digest>` holds the fingerprint of the manifest and the version of views. No file is hashed: a standing test fails when the code of an operation, or of views, derivation or representations, changes and its version does not, so a variant made by other code is never read; a bank is opened to read with `Bank(directory)` and to derive with `Deriver(directory, device, resident)`. The runner prepares variants with `--workers` and, between trials, prunes the variant cache of every bank under the runtime home together to `--variant-gb`, least recently used first; the current trial's variant is kept. One budget covers all banks, so older searches' variants give way to the active one. Preparation counts against the trial deadline.

Every variant is built by the one engine of the graphspec README, a separate graph as one segment. `graphs/join=single` joins groups of `graphs/join_size` truth graphs, each onto one step axis, and builds each group graph by graph, so memory stays near one graph whatever the group size. Groups build in parallel across `--workers`; when a split has fewer groups than workers, the workers are spread over its graphs. Windows of a joined group use a window-local entity index: the entities the window references, renumbered, instead of every entity of the group, and the batch budget counts each window's distinct observed entities. A batch draws its windows from groups covering about 64 graphs, as separate graphs do. Joined arrays up to 4 GiB are held on the training device, and resident joined graphs are evicted least recently used beyond 12 GiB. Large joined arrays use temporary memory-mapped files and bounded copies on the runtime volume. The history of periods uses sorted indexes of observations and of the first nodes of tasks. The array store retains 128 graph stores; the resident cache retains 192 graphs. Arrays over 64 MiB remain mapped, and packing transfers only requested feature rows to the training device. Observation features are stored once: a variant holds `x_ref`, one row number per observation, and the feature table `x_table`, the `obs_x` of the views of its graphs. A batch selects rows from each graph's resident arrays and concatenates only what it selected.

**Packing**

`bank/bank.py` owns bank storage and variant identity, `batches/inputs.py` builds model inputs from graph windows, and `batches/tensors.py` resolves deferred gathers onto the training device. `batches/batching.py` combines independent windows and `batches/packing.py` owns worker processes and their transfer buffers.

`recipe` prepares one window as NumPy arrays and deferred feature gathers. Numba kernels implement graph traversal and sampling; sorted indexes bound row searches. `recipe_batch` combines equal-length independent windows, and `materialise` resolves their gathers together while preserving row order and duplicates. Views whose rows do not interact (tree, walks, sequence, mixed, event graph) narrow a window's rows to the span of its supervised rows; memory and projection compute neighbour histories for supervised rows only. For the snapshot view, except with coupling edges, a batch builds each graph's overlapping frames once: the input and spatial layers run on those frames and the result is expanded to the windows, and per-window edges are built only for the graph-cell and evolving modes, which read them per frame.

`packing.Packer` prepares batches in worker processes using two shared-memory slots per worker. Worker processes start with their numeric libraries limited to the worker's thread share, which keeps an idle worker near 1 GB. CUDA receives each packed batch from a registered slot. A prefetch thread loads upcoming resident arrays within the graph-cache window; large mapped tables gather rows on demand. Small feature tables remain on the training device.

**Models**

A model is built from a model spec: a tree of parameters whose root, `view`, names the packed input the network reads, and whose other parameters switch the components that exist for that view. Every component below is read by some parameter, and every parameter is read by some component; a parameter is present in a spec only while the switch that needs it is on. `python -m tuning.fits.check` runs one configuration per switch setting and records any parameter of the built network that receives no gradient; the test suite fails on one. Each view reads the base arrays plus the representation groups listed; only those groups' parameters enter its graph spec space. Every view reads the references of a task as a set keyed by name, as [the contract](../docs/contract.md) states under What a family reads: it embeds every member node with its own machinery below, pools the members of each reference by their mean with the place of a member of an ordered reference added, projects each reference by a matrix of its own name and sums them, and reads a reference to the graph as the pooled state of the graph. Each network ends in a two-layer regression head over that readout and the projected features of the task, which hold the attributes of its graph, plus a learned embedding of the kind of the task; the head of a number reads an embedding of its series as the head of a path does. Every view that reads edges reads the relation of an edge, stated or taken from a column, through a learned embedding of its code added to what the edge carries: the message of a `relational` spatial layer, the node of a relation event, the event features of a memory, a sampled interaction partner, a node of the tree and a hop of a walk. Weights held per relation are held per table, so a table whose relations are taken from a column holds one set whatever the number of its values. `mixed`, `affinity` and `signal` read no edge. Entity numbers are graph-local correspondence keys; no network learns an embedding per entity id.

| `view` | Groups | Components and their switches |
|---|---|---|
| `snapshot` | `coupling` when `temporal` is `coupling_edges` | Encoder `Linear → LayerNorm → SiLU` plus a node-kind embedding. `spatial` propagates within each observation graph, always adding a root transform of the node's own state: `none`; `mean` of neighbours; `normalised` symmetric-degree aggregation with a self loop; `relational` one weight matrix per relation stated, table of relations taken from a column and derived relation, in each direction, plus the embedding of the relation of each edge, with edge attributes as extra messages, one mean over all relations; `attention` single-head dot-product attention; `chebyshev` a Chebyshev polynomial filter of order `chebyshev_order` in the symmetric-normalised Laplacian of the frame, one weight matrix per order; `relational_attention` dot-product attention whose keys and messages carry a learned relation embedding. `layers` stacks it, each with SiLU, dropout, residual and LayerNorm. `temporal` then orders the frames: `graph_sequence` pools one vector per frame, runs a feedback round of the tasks seen as events at the frame, pooled by their mean, and passes the frame sequence through `sequence` (`gru`, `lstm`, causal `attention` with `heads`); `entity_gru` a GRU cell per entity over its aligned frames; `entity_tcn` gated dilated causal convolutions of depth `temporal_layers`; `entity_attention` causal self-attention with `heads`; `graph_cell` a GRU whose gates convolve over the frame's edges, `diffusion_hops` 0 for the normalised convolution or K for K-hop forward and reverse random-walk diffusion, `temporal_layers` cells stacked; `evolving` a matrix GRU driven by top-k node summaries that rewrites the convolution weights each frame; `coupling_edges` message passing over the dated copies of each entity through coupling and period-boundary edges, `message` gated or attention, `temporal_layers` deep, closed by one mean propagation. Readout: the state of each member node at the frame of the task; a reference to the graph reads the mean state of the frame; with `time/context` set, each member's state passes the period-context gate over its states at the ends of earlier periods, and under `graph_sequence` the frame's state passes one over the frames at those ends. |
| `mixed` | `mixed` | Message passing over the derived-node graph with one query node per member of the references of a task, holding the member's features and receiving edges from the derived nodes its node reaches up to the task's time: `aggregation` `mean` or `attention` over edge-gated messages, `update` a GRU cell or a residual SiLU, `layers` deep. Readout: the query node of each member. |
| `event_graph` | `events` | Events as nodes linked by the event DAG and by per-entity anchors, with time and relation encodings on every edge; the kind of event an edge carries has slots of its own past every relation code and marker, so no kind of event shares an embedding with a relation; `message` gated or attention, `layers` deep. Readout per member: the mean of the events reachable from its node, or a node of its own when period context adds anchors, beside its projected features. |
| `memory` | `neighbors` when `embedding` is `attention` or `pair_terms` is on | A state per entity updated at each event tick. `update`: `mailbox_gru` builds one typed message per receiver from both endpoints' states, the event features with the embedding of its relation, elapsed time, event kind and status, means them and applies a GRU cell; `mutual_rnn` keeps two states per entity, one as the first and one as the second node of an event, updates both with RNN cells at each event of a task, and reads a member as its first state projected by log elapsed time plus its second state, offered only where tasks are seen as events; `intensity` two processes with softplus intensities over endpoint pairs, attention over the frame's edges as the neighbourhood term, then a tanh state map; `antisymmetric` integrates an antisymmetric weight matrix with `damping` by `integration_steps` Euler steps per tick, forced by event features and mean neighbour states. Readout: the state of each member node, or, with `embedding` `attention`, attention from it over its `neighbors` sampled interaction partners. `pair_terms` adds for the pair of the task the product of its two states, the frequency-weighted sum of common-neighbour states and each state scaled by its log common-neighbour count; needs `neighbors`. |
| `projection` | `neighbors` | Seeded Gaussian projections per entity, propagated one hop order per event and decayed by `decay` per order over `hops` orders in `width` dimensions. Readout per member: the Gram matrix of its projections beside its features and a mean over its `neighbors` interaction partners; for the pair of the task, the Gram matrix between the projections of its two nodes. |
| `sequence` | `neighbors` | Tokens are `neighbors` sampled interaction partners per member with time encodings, plus `structure`: `none`, `occurrence` (co-occurrence counts among the member's partners and among those of its partner in the pair of the task) or `overlap` (twelve one- and two-hop features relative to the member and to its partner in the pair, the two ends of an event of a relation without direction taken in the order of their tokens). `operator`: `mixer` token and channel MLP mixing with a mean readout; `transformer` attention over a member's tokens folded into patches of `patch` with `heads`, root-token readout; `ssm` selective state-space blocks of state width `state` over each member's tokens and over the interaction times of the pair of the task, selecting by the summary of the member's partner in the pair. `layers` deep. |
| `tree` | `neighbors` | Recursive attention over `neighbors` sampled partners at each partner's own time, from each member node, `depth` levels, time and relation encodings on tokens. |
| `walks` | `walks` | `count` causal walks of `hops` steps from each member node, anonymised by hitting counts relative to its own walks and to those of its partner in the pair of the task, encoded by a bidirectional LSTM and pooled by attention. |
| `affinity` | — | A gated linear state per member node over its counts of the kinds of task seen as events it was first of, updated by every task of the window, with a recent global profile buffer of `buffer` frames, each the mean over the tasks of its step of their members' counts and their kind; a reference to the graph reads the counts of every node. Offered where tasks are seen as events. |
| `signal` | — | A learned directed top-`topk` adjacency over signal channels, `hops` mix-hop propagations and gated dilated convolutions, `layers` deep, over the mean of the signals of the tasks of each frame; members are read by their projected features, and a reference to the graph by the state of the frame. Offered where the tasks carry signals. |

`hidden` sets every learned width except the affinity state, whose width is the number of kinds of task seen as events. `dropout` is present only where a component applies it: snapshot spatial layers, causal attention in the snapshot and sequence views, temporal-edge message layers in the snapshot and event-graph views, and mixed message layers. Event and token time gaps enter the memory, projection, sequence, tree, walk, event-graph and coupling components through `cos(w · log1p(gap) + b)` with learnable `w` and `b`; period gaps enter through linear maps of `log1p(gap)`; the mixed view carries its edge gap as a linear feature; the affinity and signal views read no gaps.

The components descend from published designs and depart from them; the names above say what runs, not which paper. For the record: the graph cell follows GConvGRU and, with diffusion hops, the DCRNN cell; the evolving convolution follows EvolveGCN-H; the mailbox update follows TGN with a mean aggregator and no edge features in attention keys; the mutual RNN follows JODIE without its trajectory loss; the intensity update follows DyRep with attention over the current frame in place of its neighbourhood matrix and without the survival loss; the antisymmetric integrator follows CTAN with a mean neighbourhood term; the projections follow TPNet; the pair terms follow TNCN; the mixer follows GraphMixer with a learnable time encoding and no link features; the transformer with `occurrence` follows DyGFormer and with `overlap` HyperEvent; the selective state-space operator follows DyGMamba without patching; the tree follows TGAT with one head; the walks follow CAWN; the affinity state follows NAViS with a regression head; the signal network follows MTGNN with one gated convolution per layer. Every path trains a regression head; none of the papers' ranking, classification or point-process losses is implemented.

References: [TGAT](https://arxiv.org/abs/2002.07962), [TGN](https://arxiv.org/abs/2006.10637), [JODIE](https://arxiv.org/abs/1908.01207), [DyRep](https://arxiv.org/abs/1803.04051), [GraphMixer](https://arxiv.org/abs/2302.11636), [DyGFormer](https://arxiv.org/abs/2303.13047), [HyperEvent](https://arxiv.org/html/2507.11836v2), [TPNet](https://arxiv.org/html/2410.04013), [CAWN](https://arxiv.org/abs/2101.05974), [TNCN](https://arxiv.org/html/2406.07926v2), [DyGMamba](https://arxiv.org/html/2408.04713v3), [NAViS](https://arxiv.org/html/2510.06940v3), [CTAN](https://proceedings.mlr.press/v235/gravina24a.html) and [MTGNN](https://arxiv.org/abs/2005.11650).

**Training protocol**

- The statement of a fit and of a search is one versioned record, `tuning/statement.py`. It holds `version`, `device`, `seed`, `seconds`, `preparation_seconds`, `workers`, `variant_cache_bytes`, `batch_sequences`, `trained`, `scored` and `sees`. `trained` and `scored` name the splits trained on and scored on, which share no split, and `sees` states for each of them the registered rules of what its tasks may see; the splits trained on are those the bank was built for. The device is `cpu`, `cuda` or `cuda:N` with N a GPU that is present; the seed is an integer from 0 to 2^32 - 1; `workers` is between 1 and the number of logical processors; seconds, bytes and batch sequences are positive integers. The record is built only through its checks. Every field is required; an absent field, an unknown field or a value outside its meaning stops the run with an error naming the field. A search builds it from `--device`, `--seed`, `--seconds`, `--preparation-seconds`, `--workers`, `--variant-gb` and `--batch-sequences`, and writes the statement of each trial to `statement.json` in the trial's directory; it is the statement of the search with the seed of the trial, which is drawn from the seed of the search and the trial's index. `config.json` holds copies of that seed and of the seconds as `seed` and `max_seconds`; a copy that is absent or differs stops the run with an error naming it. A fit stores its statement in `result.json`.
- A fit runs on the device of its statement. `cuda` with no GPU present stops with an error naming the device. Dense algebra of derivation moves to that device for a component of 1,024 nodes or more when the device is a GPU.
- The optimizer is AdamW, fused on CUDA.
- Every fit sees every row of the splits trained on exactly once per epoch, for every requested epoch, and scores every row of the splits scored on. Each epoch checks the exact row ids for omissions, duplicates and rows of other splits. A task that carries a weight enters the loss with it.
- A training window ends at a labelled step s and covers steps s−H+1 to s, with H = `time/history`. It supervises only the targets at s. Where a step may hold several tasks, a window holds at most 1,024 of them, so a step with more gets several windows over the same steps.
- With `time/context` c above 0, a window that starts in period p starts instead at the first step of period max(0, p−c). Each family gets its period-end readout. Replayed steps add no supervised rows.
- A batch groups windows of equal length, `batch sequences × 16 // H` of them. It holds at most 1,024 frames, 1,024 prediction rows, 1,048,576 entity-frames and 4,194,304 facts, where a window contributes its steps times its graph's entity count and times its graph's facts per step from the manifest.
- On a GPU the infra layer reserves the GPU memory a fit or model check may use.
- Batches hold windows of one length. They are formed within chunks of 64 graphs: each epoch shuffles the graphs, cuts them into chunks, forms every batch inside its chunk and shuffles the batches of a chunk, so the feature matrices an epoch touches are loaded about once each rather than once per batch.
- Sequence and memory states reset at window boundaries. Event models start from the last features known before the window.
- Targets are standardised per series with the mean and sample standard deviation of the rows of the splits trained on. Predictions are converted back before scoring raw MSE and R².
- The saved checkpoint is reloaded and must reproduce the first validation batch.
- The configured `--seconds` budget covers selection, layout, source capture, variant building, packing, training, and evaluation. At the deadline the runner records a timeout and waits for every owned worker to exit before continuing. Pruning runs after cleanup, outside the trial budget. Late outputs are retained with `late_` names; incomplete trials receive no prediction score. `trial.json` records phase timings.

**Search**

| Selector | How trials are chosen |
|---|---|
| `--selector forest` | SMAC-style selection: a random forest fitted to the log of completed scores predicts each candidate's MSE, the spread across its trees stands in for uncertainty, and a second forest fitted to all completed, failed and timed-out trials predicts completion. Log expected improvement over the best observed MSE, computed in log space, plus three times the log completion probability ranks 10000 uniformly drawn valid configurations. Parameters selected by `--random-params` are drawn first and held fixed. |
| `--selector botorch` | BoTorch fits a MAP-SAAS Gaussian process to completed scores and a separate feasibility model to all completed, failed and timed-out trials. Both models fit on the device of the statement, and log expected improvement ranks 10000 uniformly drawn valid configurations to pick one. Parameters selected by `--random-params` are drawn first and held fixed in every candidate evaluated by the model. |
| `--objective` | For path banks, `series=weight` pairs that blend the per-series validation losses into the one score trials are ranked by, for example `--objective level=1 trend=2`. Each series loss is its validation MSE averaged within tasks divided by the series' training variance. A new run weighs every series 1; a continued run keeps the saved weights unless new ones are given, and since every result stores each series' loss, reweighting re-ranks finished trials without refitting. Other banks rank by raw validation MSE and take no weights. |
| `--mix` | Percent of trials after the startup phase handed to each selector, as `name=share` pairs summing to 100, for example `--mix random=80 forest=10 tpe=10`; a new run states it; a continued run keeps the saved mix unless a new one is given. |
| `--selector tpe` | Optuna's multivariate, grouped TPE with 10 random startup trials, 64 expected-improvement candidates, and a good set of the best 100 trials. Model parameters are named `model/<parameter>`, training parameters by their names, settings `graph/<parameter>`, the presence of the entry N of the pipeline `pipeline/N` and its parameters `pipeline/N/<parameter>`. A model parameter enters a trial only while its condition holds; a setting only when the model's view reads its group and its condition holds; the parameter of an entry only while the entry is present and its condition holds. |
| `--selector random` | Each active model parameter, each training parameter and each active spec parameter drawn uniformly, in that order. |
| `--startup-trials N` | Minimum number of finished trials before the mix takes over; a new run states it. Completed, failed and timed-out trials count regardless of their original selector. Below this threshold new trials are random. Existing history is retained. `--random-trials` is an alias; plans retain the `random_trials` field. Legacy TPE uses this number as its initial trial-index threshold. |
| `--random-params model/view ...` | Fully qualified parameter names or wildcard patterns to keep random after BoTorch starts. Model names use `model/`, settings `graph/`, entries of the pipeline `pipeline/`, and training names are unprefixed. Draws obey the proposal bounds and remain fixed whenever active. Omission preserves a continued run's setting; supplying the flag without names clears it. |

For every proposal the runner rebuilds the optimizer from the trial files; there is no external study database. A completed result must match the frozen supervision fingerprint, cover every training row, score the complete validation split and have a finite score. Otherwise loading the result fails. BoTorch learns from the original recorded configurations, including history outside the current proposal bounds. Bounds constrain new proposals, not historical training inputs. Categorical values use one-hot encoding; numeric inputs use their declared ranges and logarithmic scales, with activity indicators for conditional values. Failed trials train feasibility without invented prediction scores. TPE retains its existing failure ranking and bound filtering. Interrupted trials are excluded from both learning and BoTorch's startup count.

`selection.json` records:

- the selector, seeds, settings, proposed parameters and failure history; BoTorch also records preset random values and every trial used for learning
- the model digest, its description, the model parameters that differ from their defaults and the model space
- the digest of the settings, the settings that differ from their defaults, and the model's space of settings; the digest of the pipeline, its flags and parameters that differ from their defaults, and the space of the template
- prior trial ids with result hashes
- the bank manifest hash, the supervision hash and the declaration fingerprint

Configuration and selection are saved before the worker starts, and a continued trial reuses them. `--bounds` narrows the space new proposals draw from; the bounds are stored in `plan.json` and in every `selection.json`. A bound on a choice or a flag that leaves out its default leaves the narrowed parameter without one, so that nothing reads a value the bound excluded.

The time limit of every trial is the `seconds` of the statement, and `--seconds` is required. `plan.json` holds copies of the statement's seed, seconds, workers, variant bytes, batch sequences, splits trained on, splits scored on and what each split may see; on continuation each copy must equal the statement given, and a copy that differs or a field that the plan lacks stops the run with an error naming it. A new run states `--selector`, `--startup-trials`, `--mix` and `--random-params`; a continued run keeps the saved ones unless new ones are given. The dashboard and result exports expose older trials' recorded budgets under the same parameter without rewriting their original configurations.

To draw epochs randomly before BoTorch chooses the remaining parameters, use `--random-params model/view epochs` with bounds `{"epochs":{"low":1,"high":5}}`. The range includes every integer between its endpoints. Bounds that hold `max_seconds` are refused with an error naming it. BoTorch learns from historical runtime limits recorded with completed and failed trials. Missing historical limits remain unknown; the current plan's limit is never substituted for them.

A trial's configuration holds the model spec under `model`, the pipeline under `pipeline`, the settings under `graph`, the splits of the statement under `splits`, the training parameters below at the top level and `seed`. A search takes its pipeline as a template, `--pipeline FILE`, a JSON list of the operations in order with their labels; a new run states it, `plan.json` keeps it, and a continued run states no other. The search draws which entries of the template are present and their parameters, never their order. Model parameters draw from these ranges; a parameter is drawn only while its condition holds. The parameters of the operations, the settings and their ranges are in [graphspec/README.md](../graphspec/README.md).

**Run directory**

The runner owns one trial at a time. Windows Job Objects and Linux process groups contain its descendants; uncertain cleanup stops the runner. `tuning.searches.records` validates trial identity, complete epoch and row coverage, finite scores, and outcome files. Completed, failed, timed-out, and interrupted attempts stay distinct; a worker that exited without an outcome is interrupted. Older plan versions require explicit migration.

| File | Contents |
|---|---|
| `plan.json` | Bank path and manifest hash, fingerprints, seed, budget, selector, workers, variant budget, the template of the pipeline and every planned trial with its model digest and description. |
| `runner.lock` | Per-run writer lock in the external run directory. Windows heavy-job singletons use user-SID named mutexes without lock files. |
| `runner.json`, `running.json` | Runner lifecycle and owner identity; active worker identity and trial. |
| `train_blocks_H.json` | The training windows for history H. |
| `trial_NNNNNN_<selector>_<model digest>_<spec digest>/` | One trial. |
| `trial_*/config.json`, `trial_*/selection.json` | The configuration, with its pipeline under `pipeline` and its settings under `graph`, and how it was chosen. |
| `trial_*/worker_NN.log` | JSON events, one per line: fit entry, training progress, epochs, validation and timing logs. A failing worker ends the log with its traceback. |
| `trial_*/source/` | The `tuning`, `graphspec` and `graphspec.infra` sources the worker ran. |
| `trial_*/result.json`, `predictions.npz`, `checkpoint.pt` | Scores, timings, parameter count, peak GPU memory and row hashes; validation predictions; weights. |
| `trial_*/failure.json`, `timeout.json`, `fit_progress.json` | Failure records and the budget heartbeat. |

`--trials N` ends a continuous run once N trials are recorded; a continued run takes the limit it is given. A file named `STOP` in the run directory stops the run after the current fit, and stops a continued run before its first trial. The runner refuses to continue while the worker named in `running.json` is still alive.

**Verification**

`python -m tuning.fits.check BANK --output checks.json --device cpu|cuda --seed N --trained ... --scored ... --sees ... --pipeline pipeline.json --settings settings.json [--graph N]` runs forward, backward and checkpoint reload for one model spec per setting of every structural switch the bank offers, and records any parameter that received no gradient. Each derives its variant by the stated pipeline, with the settings its groups read taken from `settings.json`, which states every setting any of them reads; a setting it lacks stops naming it, and a key that no view's settings declare is refused. It runs on the last window of graph `N`, or of the graph with the most observations. A model that runs out of GPU memory is recorded and the check continues; the command then exits with the list of those models. Any other error stops it.

Two switches apply across views. `time/encoding` picks the time-gap encoding every temporal component uses: `log_cosine` is `cos(log1p(gap) w + b)` with learnable `w`, `cosine` the same on the raw gap, `log_linear` a linear map of `log1p(gap)`. `keys/embedding` adds a learned vector per entity key, hashed into a table of `keys/table` rows, to every entity encoder of the view: observation nodes, derived nodes, event endpoints, memory states, tree, history and walk nodes, and the member nodes of the references of a task. Only node types whose keys recur across graphs receive it: a bank marks a type shared when at least half of its distinct keys appear in two or more graphs, and other types get a zero vector, so identifiers that are unique to one graph never carry an embedding that could memorise the graph they came from. The table is a parameter trained by the training rows only, so holdout graphs see vectors learned from training graphs that contain the same key.
